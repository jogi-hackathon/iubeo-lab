## WJ topology 確認（実コード）

`WasmJitWarp.cpp` + `gecko.js/lib/wasm-host-bridge.js`:
- **1 JIT 関数 = 1 wasm module = 1 instance**（`new WebAssembly.Module` 同期）
- 全 JIT fn の `m` export を共有 `WebAssembly.Table`(anyfunc, 4096) に登録
- JIT→JIT call = `call_indirect` via shared table → **callee は別 instance**
- guest memory は JIT module が import して直読み（ミラーなし）
- 既存: `m.help` 単一 op リカバリ helper(id=-3)、`m.call` C++ 再入 fallback(id=-2)、
  `kWJEHABI` タグセクションの足場あり
- 再コンパイル時は同じ table slot を再利用（IC が funPtr→slot を cache するため）

「小さい hot 関数を頻繁に呼ぶ」call-heavy コード。

# Cohort v1 (Hotpack) 実装・計測 2026-10-03 続報

実装: `GECKO_WJ_COHORT=N` で有効化。solo compile 時に emit 済み body bytes を
`WJEntry::jitBody` にキャッシュし、pending が閾値に達する/idle 境界で
`WJWarpCompileCohort` が **body バイトコピーのみ**で N 関数を 1 module/1 instance
に再組立（Warp 再実行なし・再コンパイルコスト≈0）。call IC fill 時に観測した
caller→callee エッジ (`gWJCallEdges`) を記録し、drain はエッジ両端を優先 packing
→ member の既存 shared-table slot は維持（callers の cache 済み IC は無傷）、
tramp/member export は `f`/`f1..`, `m`/`m1..`、host direct path は
`wasmhost_call(handle, -(memberIdx+1))` で member 選択。

変更点:
- `WJEntry` +`memberIdx`/`cohortId`/`jitBody`; 全 `wasmhost_call` 経路が memberIdx
  を渡す（entry 通常 call / WJH_CALL callee / ctor fast+slow path / construct cache）
- `wasmhost_jit_table_set(handle, slot, member)` 3 引数化（両 bridge）
- drain: `pending >= cap` 同期 + `WasmJitDrainDeferred` idle 境界。エッジ駆動 pack
  → transitive 引き込み → 残り seeds で pad。`cohortId>=0` の member は再 pack しない
- ctor cache (gWJCC_*) は cohort install 時に旧 handle→新 handle/member を repoint
- invalidate-all は memberIdx/cohortId/jitBody/pending/edges もリセット
- stats: `cohorts` / `cohortMembers` / `cohortEdgePulls`

計測 (embed, node `bench/main.ts`; マシン負荷で絶対値は ±2x 変動するため
交互実行・中央値/最小値で判断):

| bench | solo | cohort | 備考 |
|---|---|---|---|
| call-chain (16 callee chain) | 28-44ms | 22-28ms (iters=60) | **~15-30% 改善**, sum 一致 |
| call-chain (iters=30, 短い) | 20.0-21.4 | 19.5-19.9 | ~3%（tier-up 前は小さい） |
| richards | ~6100 | ~6080 | 誤差内 |
| deltablue | ~1889 | ~2072 med | 誤差内〜微増（再 compile コスト除去後） |
| micro 全 21 bench | sum 全一致 | sum 全一致 | 正確性回帰なし・速度はノイズ範囲 |
| octane 11 bench cohort 完走 | - | crash なし | smoke OK |

確認できたこと:
- エッジ記録は動作: deltablue で 4 cohort × 16 member、sites=105 edgePulls=79
- 効果は「hot な caller→callee が両方 compiled で同 cohort に入る」workload に限定される
  → call-chain のような dense chain で顕著。octane は効果がノイズ以下
- 旧設計（drain で Warp 再実行）は deltablue で ~5% の回帰を招いた
  → body キャッシュ方式で解消（assemble はバイトコピーのみ）

残る論点:
- drain トリガー = pending>=cap のため cap>compiled 総数では不発
  （idle boundary drain が網羅するが bench 中は発火しにくい）
  → 追記: IC fill（エッジ記録）時に `pending>=min(8,cap)` で発火するよう変更済み。
    cap=64 でも call-chain で cohort 形成を確認
- エッジは JIT-compile 済み callee のみ有効; PBL callee は pack 対象外
- `jitBody` メモリ増（関数あたり emit bytes 保持 — 小）
- GC: `gWJCallEdges`/`gWJCohortPending`/`gWJCallSiteScript` は WJTraceRoots で trace 済み
- compacting GC で jitBody 内に焼かれた生ポインタ系 immediate は
  solo emit と同じ前提（既存コードと同等の hazard 範囲）

-20~30%、site workload では害なし。
